# Revsense (Waveshare OBD gauge, repo name Tachi)

Revsense: a round dash gauge for a 2025 Mazda 3 (the project and repo were first called Tachi). An ESP32-S3 round touch display reads live engine data from a BLE OBD-II adapter and shows it on dial-style pages. It starts with the Revsense welcome (the gauge draws itself, then the wordmark fades in; a touch skips it). The old animated Tachi faces and their welcome are still in the code but hidden (`SHOW_PAGE_FACE`, `MOCHI_INTRO` in `config.h`, set to 1 to bring them back).

## Hardware

- **Board:** Waveshare ESP32-S3-Touch-LCD-2.8C: 2.8" round IPS 480x480 (ST7701 on 16-bit parallel RGB), GT911 capacitive touch,
  TCA9554 I/O expander, ESP32-S3 with Wi-Fi + BLE 5, 16 MB flash, 8 MB PSRAM, QMI8658 IMU, PCF85063 RTC, buzzer, TF slot.
  No RGB LED.
- **OBD adapter:** advertises as `CodeReader31B` (dual-mode Classic + LE). This firmware uses its BLE side only (the ESP32-S3 has no Bluetooth Classic).
- **Car power:** 2025 Mazda 3 USB-C port, through a USB-C cable.
- **USB:** the cable can go in either USB-C port. The UART port (CH343 chip) is what flashes and resets reliably; the firmware's serial log goes out the native USB port.

## Pins and drivers

- Pins and panel timings: `include/board_round28.h` (from Waveshare's demo). Display and touch driver: `src/display_round28.h`; the ST7701 init
  command list is in `src/round28_init.h`.
- The ST7701 needs its chip-select (on the expander) toggled around **each** init command (`st7701Init()`). Holding it low for the whole
  sequence, as Arduino_GFX's batch init does, leaves the screen backlit but blank. Pixel clock is 18 MHz.
- Only the expander pins we use (LCD reset, touch reset, LCD chip-select) are driven; the other expander pins, including the buzzer, stay inputs.

## What it shows

Everything is drawn into a 480x480 canvas in PSRAM. Swipe left / right for the next / previous page (`SWIPE_NEXT_ON_RIGHT` in `config.h` flips it),
tap for the next page, touch and hold about 1.5 s for demo mode. The BOOT button works as a tap. Pages, in order (set `SHOW_PAGE_*` to 0 in `config.h` to hide):

1. **Face**: the animated character (`src/mochi.h`) on a dithered navy-to-indigo gradient, drawn at `FACE_SCALE` (1.6x).
2. **Sport**: segmented RPM ring, big speed, RPM, coolant / fuel / battery chips.
3. **Tach** and 4. **Speedo**: analog dials with a needle (0-160 mph).
5. **Vitals**: four ring gauges: coolant, fuel, battery, load.
6. **Arc** and 7. **Custom** (boost): a 270 degree boost sweep (manifold pressure minus barometric, psi or bar from Settings), Custom adds three icon readouts.
   These two appear only if the car answers manifold pressure (PID 010B).
8. **Quad**: four values at once (torque, intake air, fuel, load by default; torque needs the car to answer PID 62, and 63 for Nm / lb-ft). 9. **Dual** (TEMPS): coolant with a bar (`DUAL_ROWS` takes one or two values; one is centred). What the Custom / Quad / Dual pages show is set by `CUSTOM_ROWS`, `QUAD_CELLS`, `DUAL_ROWS`.
10. **Gear**: the estimated gear (1-6, N when stopped, - when unsure), a 1-6 ladder and the speed. OBD has no gear value, so it is worked out from RPM and speed with the ratios in
    `src/gear.h` (a guess for the Mazda 3: tune from a drive). The P R N D S M selector is not available through standard OBD.
11. **Brightness**: a glowing sun, a slider and four preset chips (25 / 50 / 75 / 100 %). The level is saved across restarts.
12. **Debug** (always last): link state, raw adapter exchanges, build stamp, boot type, gear test result.

The dial pages draw in `src/round_ui.h` with anti-aliased Krona One digits (`src/round_font.h`, generated by `tools/fontgen/fontgen_round.py`, SIL OFL font).
A frame only touches what changed and sends just those rows to the panel, after the panel's scan has passed them (a vsync hook in `display_round28.h` plus `waitBeamPast()`), so the needle does not tear.
The Face page sends its area without waiting (faster); the serial log prints `dial N: X fps ...` every 2 s on a dial page.

**Status screens** (scanning, connecting, adapter not found, link lost): an animated page with a short title, a helper line and a SCAN / CONNECT / LIVE step row.

## What it does

- Scans for the adapter by name, connects over BLE, sets it up (`ATZ ATE0 ATL0 ATH0 ATS0 ATSP0`), reconnects automatically if the link drops.
- Polls back-to-back with separate requests for speed (`010D`) and RPM (`010C`) every cycle, and coolant (`0105`) / oil temp (`015C`) and extra gauges in turn
  (about 5-6 cycles/s on the Mazda 3). Tested on the car and found NOT to help, so they are off: the combined `010C0D` request, the engine-only filter `ATCRA7E8`
  (not accepted) and the trailing-`1` reply count (much slower). Two modules answer every request (replies come back twice, e.g. `410D00410D00`); the first is used.
- At connect the board reads which standard values the engine computer supports (bitmaps 0100/0120/0140/0160, shown as `sup:` on the Debug page).
  Battery uses the adapter's own voltage reading (`ATRV`, works with the engine off), with the car's control-module voltage as fallback.
- **Animated character:** glowing eyes that morph between 27 expressions (pictures in `docs/preview/`), and a welcome at power-on: two headlights appear far away, a car drives in and brakes,
  the lamps flash and become the eyes, the eyes turn into happy arches while a glowing "TACHI" writes itself on, then the normal face returns (about 5.4 s).
  After a quick restart (the car's USB power can dip while cranking) a short 0.9 s version plays; `INTRO_FORCE` in `config.h` forces full or short.
  Random idle behaviour (looks around, smirks, sneezes; Police / Headlights / Glitch only while parked). It runs in its own task so Bluetooth polling cannot stall it.
  Demo mode replays the welcome and then shows every expression with its name.
- **Moods** (checked in this order, thresholds in `config.h`): sleepy (no valid data for 5 s), worried (coolant >= 108 C), uneasy (>= 100 C),
  excited (RPM >= 3500, or speed rising >= 8 mph/s), calm (cruising >= 55 mph with RPM < 2600), happy (everything else).
  Mood -> expression: happy = default, uneasy = sweat drop, worried = angry, sleepy = sleepy, excited = turbo eyes, calm = squint.
- **Car events** on the Face page (`CAR_EVENTS`, thresholds in `config.h`, logic in `src/car_events.h`, tested by `tools/tests/car_events_test.cpp`):

  | Event | When | Face |
  |---|---|---|
  | Engine start | RPM was low for 3 s, now above 500 | sparkle |
  | Hard braking | speed 15+ mph drops 10+ mph in a second | startle |
  | Redline | RPM reaches the redline (`RPM_REDLINE`) minus 250 | glitch flash, once per visit |
  | Hard launch | speed jumps 6+ mph in a second from below 25 mph with 3000+ RPM | laugh |
  | Smooth stop | the car stops without hard braking | content (UwU) |
  | Engine off | RPM falls to zero after the engine was running | drifts off to sleep |
  | Engine warm | coolant reaches 80 C after a cold reading, once per power-up | happy / love |
  | Low battery | engine running, under 11.5 V (at most once a minute) | crying |
  | Low fuel | under 7 % (at most once in 2 minutes) | crying |

  Each has its own cooldown. Skipped during the welcome and the settle period and in demo mode; they play only while the Face page is shown.
- **Gear test** (`GEAR_SNIFF_TEST`): at the first connection it listens about 45 s for the CAN message that the open-source Mazda definitions list as the gear selector (ID 0x01F)
  and reports what it saw on the Debug page and Serial. Set it to 0 once you have the result.
- Temperatures, speed and pressure units are chosen in Settings, Units (the car itself reports deg C and km/h). Mood thresholds stay in deg C.
- Serial log (115200) of every command and raw reply, and of every BLE device seen during scans.
- microSD logging exists in the code (`SD_LOG_ENABLED`) but is off: the TF slot shares pins with the display's init bus and has not been confirmed.

Not included yet: sound, motion sensing, Wi-Fi.

## Files

- `platformio.ini`: the board, platform and libraries (NimBLE-Arduino 2.x, GFX Library for Arduino). Two environments: `waveshare_s3_round28` (the firmware) and `waveshare_s3_round28_test` (display + touch test).
- `include/config.h`: settings (adapter name and UUIDs, thresholds, pages, timing). `include/board_round28.h`: pins, panel timings, layout.
- `src/main.cpp`: BLE / OBD, moods, the UI loop. `src/display_round28.h`, `src/round28_init.h`: panel and touch. `src/round_ui.h`, `src/round_font.h`: dial, brightness and status pages.
- `src/mochi.h`, `src/scaled_gfx.h`: the animated character and its scaler. `src/car_events.h`, `src/gear.h`, `src/obd_parse.h`: pure logic with host tests in `tools/tests/`.
- `tools/preview/`: render the face and pages on a computer; `round_ui_selftest.cpp` must print PASS. `tools/fontgen/`: font generators. `hardware/enclosure/`: a 3D-printable case.

## Build and upload

1. Install VS Code and the PlatformIO extension, open this folder. (PlatformIO's own Python must be 3.10 or newer for the ESP32 platform.)
2. Plug the board in. If no serial port appears, hold BOOT while tapping RST.
3. Select `waveshare_s3_round28_test` first (a test picture and a dot at each touch), then `waveshare_s3_round28`, and click Upload. The first build downloads the platform and libraries.
4. Open the serial monitor at 115200. The Debug page shows the build time and a feature tag, so a photo proves which firmware is on the board.

## Verified vs. unverified

**Verified on hardware:** the display, backlight, touch, PSRAM, the dial pages, swipe, brightness, the status screens and the animated face run on a real 2.8C board. The BLE adapter name and UUIDs were read from a phone screenshot:
`CodeReader31B`, service `FFF0`, `FFF1` notify (adapter -> board), `FFF2` write (board -> adapter). The adapter accepts only one connection at a time.

**Not yet verified:** the gear test result (needs the car), boost on the Mazda 3 (does it answer PID 010B?), the gear ratios, and the car-event thresholds on a real drive.

## Known issues / ideas

- Mood thresholds are for coolant in deg C and may need tuning for the Mazda.
- If the adapter lacks a prompt `>` after some replies, commands will time out.
- Ideas: a rev-match helper on the Gear page, sound (an external player on the UART header), IMU reactions, the Google Maps turn card.
- Power only needs 5 V from USB. The board's operating temperature range is unchecked: avoid leaving it on a hot dash.

**Screen sleep:** the car's USB port stays powered after the engine is off. After `SCREEN_OFF_AFTER_MS` (2 minutes) without car data the backlight goes fully dark and nothing is drawn; fresh car data lights it at once, and a touch or the BOOT button lights it for `SCREEN_WAKE_MS` (30 s). The touch that wakes the screen does not also change the page. The logic is `src/screen_sleep.h` (tested by `tools/tests/screen_sleep_test.cpp`). The board itself and Bluetooth keep running, so for zero draw use a switched USB cable or an ignition-switched fuse tap.

**Drive report and trip history** (`SHOW_PAGE_TRIP`, `src/trip.h`, `src/report_view.h`; tested by `tools/tests/trip_test.cpp` and `report_view_test.cpp`):
- A trip starts when the engine runs and ends when the engine has been off (or the car silent) for `TRIP_END_MS` (30 s). Trips under `TRIP_MIN_S` (90 s) or `TRIP_MIN_MILES` (0.2 mi) are thrown away. When a trip ends the Drive report page opens by itself and the screen stays on for a while.
- The page shows top speed, max RPM, max coolant, peak boost (vacuum shows negative on a non-turbo engine), battery volts range, and new fault codes, plus duration, distance, hard brakes and hard launches. Values the car does not give show `--`. The chips under the tiles pick the live trip or one of the last 5 saved trips.
- There is no grade or score any more: the screens show only the measured values. (The tracker still stores an internal rating number in each saved trip so older saves stay readable; nothing shows it.)
- The last 5 trips are kept in the board's flash (about 270 bytes); the running trip is saved every minute, so if the USB power is cut the trip is recovered at the next start. Demo mode never makes a trip.

**Fault codes** (`SHOW_PAGE_CODES`, `src/dtc.h`, `src/dtc_text.h`; `tools/tests/dtc_test.cpp`):
- After connecting, at the start of a trip, every `CODE_CHECK_MS` (the check-engine light and count, PID 0101; a rising count triggers a read) and when you tap READ AGAIN, Tachi reads the stored (mode 03) and pending (mode 07) codes. Both modules' answers are combined. About 100 common generic codes have a short description; others say "see service manual".
- A code that was not there when the trip started is tagged NEW and counted in the drive report.
- **CLEAR** (mode 04) needs a 3 second press-and-hold on the button (`CODE_CLEAR_HOLD_MS`) and is refused while the engine is running. A touch that only woke the screen can never press a button. Clearing also resets the car's emissions readiness monitors and the saved freeze-frame data, so do not clear just before an emissions test. Nothing is ever cleared automatically. Demo mode shows made-up codes and sends nothing to the car.

**G-force page.** A performance-car style friction circle (rings at 0.5 and 1.0 G, a glowing dot, a fading trail of the last second, an amber peak marker, the total G and the peak on top). It reads the board's own QMI8658 motion sensor (same I2C bus as the touch chip, read only by the UI task), so it needs nothing from the car; the page is hidden if the sensor is not found (`SHOW_PAGE_GFORCE`). `src/gforce.h` (tested by `tools/tests/gforce_test.cpp`) does not depend on how the board is mounted (tilted, turned, even upside down): accelerate / brake G is how fast the car's OBD speed changes (a straight-line fit over the last ~0.8 s, so it lags by about a third of a second), and cornering G is speed times the gyro's yaw rate (the rotation about the vertical axis, found from the direction of gravity while the car is still; a clockwise turn is a right turn, so nothing has to be learned on the road). The gyro's resting offset is learned while the car is still. With no speed reading the page shows zero. The ZERO chip takes the current position as level and clears the peak. Demo mode shows a made-up drive. Not yet tried on the board and in the car.

**Welcome and branding.** `src/brand.h` draws the welcome (ring, red arc and needle sweep, hub pulse, then the "Rev" + "sense" wordmark, 3 s; only the pixels that changed are redrawn each frame, so the sweep stays smooth); the wordmark is a bitmap cut from `tools/brand/revsense_logo.png` by `tools/brand/make_logo.py` (the UI fonts are capitals only). It is skipped after a quick restart (the engine cranking) and by a touch. `tools/preview/brand_preview.cpp` renders it and checks the dirty boxes. The storage name `tachi` is kept so saved settings and trips survive.

**Gauge styles (Settings, Theme, GAUGE row).** The Tach and Speedo pages come in three styles, chosen independently of the colour theme (so every look and colour works with every style): DIAL (the needle dial), ARC (a thick arc that fills with the value, numerals 0..7 inside it, the value in big square block digits, "RPM" below) and TICKS (a ring of fine ticks that light up with the value, numerals inside, small "RPM" in the middle, the value in block digits at the lower right). Both new styles use the square one-cell-stroke block font in `round_ui.h` (`blk`, `blkNum`) and turn red past the redline. The choice is saved in its own flash key (`gauge`), so the main settings blob stays valid.

**Navigation (turn-by-turn from Google Maps).** The board is also a Bluetooth peripheral called "Revsense" (next to its link to the OBD adapter). The Android app in `android/` reads the Google Maps navigation notification and writes each turn to the board (`N|code|metres|street`, see `src/nav.h` and `android/README.md`); the **Navigation** page then shows an arrow, the distance (feet / miles or metres / km, following Settings > Units), the street and a bar that fills as the turn gets close. The page only appears while a phone is connected or a route is running (it goes away 20 s after the last update); demo mode shows a made-up route. `nav.h` is tested by `tools/tests/nav_test.cpp`. The board side works with any app that writes those lines (test it with nRF Connect); the phone app has not been built or run on a phone yet.

**Page order and Settings.** The swipe order is Tach, Speedo, Arc (boost), G-force, Navigation (only while a route is running), ENGINE (torque, intake, load), HEALTH (coolant, battery, fuel), Drive report, Trip history, Fault codes, **Settings** (the Face, Cluster, Custom, Vitals and Gear pages are hidden: `SHOW_PAGE_FACE`, `SHOW_PAGE_CLUSTER`, `SHOW_PAGE_CUSTOM`, `SHOW_PAGE_VITALS` and `SHOW_PAGE_GEAR` in `config.h`, set to 1 to bring them back) ENGINE and HEALTH use the triangle layout: a Y splits the round screen into three sectors (left, right, bottom), each with a label, a value and its unit; the left and right values also have an arc along the rim, the bottom one a short bar (`QUAD_CELLS` / `HEALTH_CELLS` in `config.h`). Battery is part of HEALTH now, so the standalone Battery page is hidden (`SHOW_PAGE_BATTERY`, set 1 to bring it back). Settings is always last ( a `static_assert` in `main.cpp` keeps it there, so new pages go before it). Brightness and Debug are not pages of their own: they are inside Settings. The hub lists them as rows (icon, name, current value); tap a row to open it, tap BACK (or swipe) to return. Inside a sub-screen a stray tap does nothing, and swiping away from Settings always returns it to the hub. The hub has five rows: Brightness, Units, Warnings, Theme, Debug.

**Units, warnings, themes.** All three are saved in flash (`src/settings.h`, a validated blob, so a damaged or older save falls back to the defaults) and apply at once, on every page, the drive report, the face moods and the event reactions.
- *Units*: speed mph / km/h (the speedo dial switches to a 0 to 280 scale), temperature F / C, pressure psi / bar. Values are stored as mph / deg C / psi and converted only for display.
- *Warnings*: tap - or + to change the coolant warm and hot levels, battery low, fuel low and the redline (shift lights, red zone). The compile-time values in `config.h` are only the defaults now.
- *Theme*: tap LOOK to cycle CLASSIC, SPORT RED, ICE SILVER, TRACK ORANGE and REVSENSE (the logo red on neutral dark greys, the default on a fresh install; a theme you saved earlier is kept) (our own colour moods: gradient, accent, bezel and panel tones, `src/theme.h`), tap COLOUR to swap the accent for cyan, green, amber, orange, red or violet. A gradient bar previews the choice.
Not compiled or run on the board yet: the host tests (`tools/tests/settings_test.cpp`, `theme_test.cpp`), the layout checker and the draw self-test cover the logic and layout.

**Connecting.** Scanning, connecting and link-lost screens show how long the wait has lasted, and after 15 s they say "tap to skip": touching the screen hides the status screen so the normal pages (with `--` values) can be used while Tachi keeps connecting in the background; it comes back if the link is lost. A setup that gets no answer to two commands in a row is abandoned and retried, and the Bluetooth client is rebuilt after any failed attempt. The gear-selector sniffing test (`GEAR_SNIFF_TEST`) is off: it kept the screen on "SHIFT P R N D" for about a minute after every power-up and found no gear data anyway.

**Drive report and Trip history.** They are two pages. The Drive report shows the live trip while you drive (or the last finished one) as a list of six rows (label left, value right); its TRIPS button opens the Trip history, a list of the live trip and the last 5 trips (number, time and distance). Tap a row to open that trip on the Drive report page; swiping away returns the Drive report to the latest trip.

**Checking the layout without the board.** `tools/preview/round_ui_layout_check.cpp` renders the Drive report, Fault codes and Settings pages with worst-case text and fails on any text outside the round panel, overlapping text or boxes, text wider than its pill or button, descriptions wider than a code row, and fonts outside the page type scale (label, small, title and medium text). `round_ui_selftest.cpp` checks the incremental drawing, `round_ui_preview.cpp` writes pictures.
